# Raylight Windows V100 推理专用 FSDP 下一阶段计划

日期：2026-08-15<br>
状态：已批准，准备执行<br>
目标平台：原生 Windows、2× Tesla V100-SXM2-16GB、TCC、NVLink/CUDA P2P

## 1. 阶段目标

在保留现有 Raylight Windows CUDA P2P/Ulysses 速度模式的基础上，新增一个以显存容量为首要目标的“推理专用 FSDP 显存模式”。该模式通过两张 V100 分片保存模型权重，使单张 16GB V100 无法稳定容纳的模型有机会在双卡上完成推理。

本阶段不把两张 16GB 显存描述为统一的 32GB 显存池，也不承诺 FSDP 模式一定快于单卡。模型层计算时仍可能临时聚合完整层权重，激活、缓存和临时缓冲区也不会全部减半。

## 2. 与上一阶段的关系

上一阶段已经实现并验证：

- Windows 双进程、双 V100 的 CUDA IPC/P2P 数据通道。
- 为 Ulysses 等分 `all_to_all` 提供专用同步传输。
- Gloo 只承担控制面通信，主要 CUDA 张量不经过 CPU 中转。
- TCC 下 NVLink/P2P 可用；WDDM 实测无法建立 CUDA Peer Access 和跨进程 CUDA IPC。

上一阶段明确没有实现：

- 通用 NCCL 替代。
- 通用第三方 PyTorch ProcessGroup。
- Windows FSDP/DTensor 权重分片。
- 多机、任意 world size、训练反向传播集合通信。

本计划将“Windows 推理专用 FSDP”作为独立后续能力，而不是把现有专用 `all_to_all` 直接宣称为 NCCL 或 FSDP。

## 3. 运行模式规划

### 3.1 速度模式（保留）

- Ulysses=2，FSDP关闭。
- 模型权重每卡一份。
- 使用现有 CUDA P2P `all_to_all`。
- 目标是继续优化双卡相对单卡的生成速度，最终目标仍为热启动快于单卡至少20%。

### 3.2 显存模式（本阶段主目标）

- 优先实现 FSDP-only 推理路径。
- 模型权重在两卡间分片保存。
- 只实现推理实际需要的 CUDA 集合通信和同步语义。
- 第一验收目标是运行单卡16GB无法稳定完成的模型或配置，而不是速度领先。

### 3.3 混合模式（后续条件目标）

- 在同一组两张 V100 上同时启用 FSDP 和 Ulysses。
- 只有速度模式和显存模式分别稳定后才开始。
- 单独评估通信竞争、显存峰值和性能，不与前两种模式共用速度结论。

## 4. 硬性平台条件

### 4.1 TCC为强制条件

当前双 V100 平台只支持在 TCC 下进入本阶段：

- 启动前必须确认两卡均为 TCC。
- 必须通过 `cudaDeviceCanAccessPeer`、CUDA IPC 和双向 P2P 带宽探针。
- 任一检查失败时禁止进入 FSDP 数据面，不能静默回退到 CPU/Gloo。

WDDM只用于显示驱动场景，不作为本阶段可支持后端。此前实测WDDM下两张V100无法建立Peer Access，跨GPU传输退回主机/PCIe，Raylight在初始化阶段失败。FSDP会在多层之间频繁聚合权重，对低延迟、高带宽P2P的依赖高于现有Ulysses路径。

### 4.2 固定首发范围

- 原生 Windows。
- 两张相同的 Tesla V100-SXM2-16GB。
- world size=2。
- 单机、单节点。
- 推理，不支持训练。
- 先支持经过验证的模型和工作流，不承诺任意模型自动兼容。

## 5. 技术路线

### 5.1 推荐路线

扩展当前 CUDA IPC/P2P 数据面，构建一个“推理专用 CUDA Collectives”层，并通过清晰的传输接口与 Raylight、PyTorch FSDP/DTensor 集成。

首批候选能力：

- CUDA tensor `all_gather` / `all_gather_into_tensor`。
- `broadcast`。
- barrier、错误传播、超时和 rank 一致性检查。
- DeviceMesh/DTensor 在实际推理中要求的最小接口。
- 只有通信追踪证明需要时，才加入 `reduce_scatter`。

Gloo继续用于进程发现、小型元数据和控制信令，禁止大型CUDA权重张量经CPU中转。

### 5.2 暂不选择完整NCCL移植

NVIDIA已在路线图中考虑Windows支持，但当前发布版尚未正式提供；PyTorch Windows NCCL也没有可直接使用的官方路径。自行移植完整NCCL还需要维护PyTorch ProcessGroupNCCL、Windows IPC/bootstrap、构建系统、ABI和V100/sm_70兼容，工作量和维护风险显著高于本阶段目标。

设计中保留后端抽象：未来官方Windows NCCL和PyTorch支持成熟，并通过V100/TCC验证后，可以替换底层通信实现，而不重写Raylight模型集成。

## 6. 分阶段实施

### Phase F0：通信需求追踪与可行性冻结

目标：不凭猜测确定Raylight FSDP推理实际调用的集合通信、dtype、大小、顺序、同步方式和DeviceMesh依赖。

任务：

1. 梳理 Raylight、`comfy_dist`、PyTorch FSDP/DTensor 的模型加载和前向调用链。
2. 在不启用大模型正式生成的最小测试中记录实际 collective 调用。
3. 区分推理必需调用与训练专用调用。
4. 确定需要第三方 ProcessGroup，还是可通过更小的 functional collective/通信适配层接入。
5. 输出“最小集合通信接口清单”和失败风险清单。

阶段门：只有接口范围明确，并确认不需要先实现完整NCCL语义，才进入F1。

### Phase F1：双卡CUDA all-gather原型

目标：在两个独立Ray worker之间完成正确、可重复的CUDA权重聚合。

任务：

1. 实现同步 `all_gather` 原型和严格的 rank/shape/dtype 校验。
2. 使用 CUDA event 与进程级超时区分通信超时和上游 rank 停顿。
3. 覆盖 FP32、FP16、BF16存储场景及不规则尾块。
4. 测量不同分块大小、层级张量大小和双向并发效率。
5. 禁止CPU/Gloo数据面回退。

阶段门：正确性测试全部通过，通信带宽和显存开销达到F1验收标准后进入F2。

### Phase F2：最小FSDP模型集成

目标：用小型可核对模型证明参数确实分片、前向结果正确、峰值显存下降。

任务：

1. 接入最小DeviceMesh/DTensor/FSDP推理路径。
2. 验证模型加载、权重分片、逐层聚合和释放顺序。
3. 对比单卡、双卡非分片、双卡分片的输出和显存。
4. 完成异常退出、worker重启和资源释放。

阶段门：输出一致、每卡持久权重显存显著下降、连续运行无泄漏后进入F3。

### Phase F3：Raylight + ComfyUI + LTX集成

目标：在现有Raylight节点中增加清晰的显存模式，并完成5秒、10秒工作流验证。

任务：

1. 将功能放在独立开关后，默认不影响现有速度模式。
2. 增加启动前TCC/P2P/IPC能力门禁。
3. 记录每个rank的模型加载、权重聚合、采样和卸载时间。
4. 监控两卡显存、系统内存、提交量和分页文件。
5. 检查视频、音频、NaN/Inf和输出质量。

阶段门：满足F3质检标准后，才把显存模式标记为实验可用。

### Phase F4：混合模式与性能优化

目标：评估FSDP与Ulysses同时启用是否具有实际价值。

任务：

1. 分离并测量权重 `all_gather` 与序列 `all_to_all` 的通信占比。
2. 评估通信串行、双流并发、预取和缓冲区复用。
3. 根据模型大小自动推荐速度模式或显存模式。
4. 只有确有收益时才发布混合模式。

## 7. 质检与验收标准

### 7.1 正确性

- 多种形状和dtype的双rank集合通信结果逐元素正确。
- 不规则分块、零长度边界和错误输入能够明确失败。
- FSDP推理输出与非分片基线在合理误差内一致。
- 生成视频和音频无黑屏、NaN或Inf。

### 7.2 显存与内存

- 每卡持久模型权重显存相对双卡复制模式下降目标为35%～45%或更高。
- 临时完整层权重、激活和通信缓冲区峰值不超过16GB。
- 正式数据面不借用系统分页文件存放权重。
- 工作流结束后显存、共享内存和CUDA IPC句柄可以回收。

### 7.3 通信

- 启动日志明确显示TCC、Peer Access、CUDA IPC和所选通信后端。
- 大型CUDA collective不得静默回退到Gloo/CPU。
- 记录有效带宽、分块效率和等待时间，而不只记录总生成时间。
- rank进度偏差必须能定位到具体阶段，不能仅靠放宽超时掩盖。

### 7.4 稳定性

- 5秒与10秒工作流分别连续运行至少5次。
- 无死锁、rank失步、worker孤儿进程和持续显存增长。
- 失败时两边rank都能退出，并给出首个真实错误。

### 7.5 性能目标分离

- 速度模式：最终目标仍为双卡热启动比单卡热启动快至少20%。
- 显存模式：首要目标是完成单卡16GB不能完成的模型/配置；速度单独报告，不伪装成速度优化。
- 混合模式：只有同时保持显存收益且具有可重复的实际性能价值时才保留。

## 8. 预估工作量

- F0通信追踪和范围冻结：3～5个开发日。
- F1～F2推理专用FSDP原型：2～4周。
- F3 ComfyUI/Raylight集成与稳定性：累计4～8周。
- 完整Windows NCCL + PyTorch维护分支：至少8～16周，不列入当前主路线。

以上是风险区间，不是工期承诺；每一阶段都通过阶段门后才进入下一阶段。

## 9. 风险与退出条件

- PyTorch FSDP/DTensor若强制依赖无法由最小后端满足的ProcessGroup异步语义，需要重新评估接入层。
- V100/sm_70对未来官方Windows NCCL或新PyTorch版本的支持不能预设成立。
- FSDP降低持久权重显存，但可能因逐层聚合显著降低推理速度。
- 两张卡同时承担FSDP和Ulysses通信，可能互相争用NVLink。
- 如果F2无法证明显著持久显存下降，或必须实现接近完整NCCL才能继续，则暂停实现，保留现有速度模式。

## 10. 代码与发布策略

- 从当前稳定的 `windows-v100-p2p` 成果建立独立开发分支，建议命名 `windows-v100-fsdp-p2p`。
- 现有速度模式在新功能通过验收前保持不变。
- 所有实验能力均放在显式开关后，不自动启用。
- 每个阶段保存小型测试、结果摘要和可复现实验条件。
- 本计划只先写入本地；代码、文档和测试通过阶段性复核后再决定是否提交和推送GitHub。
